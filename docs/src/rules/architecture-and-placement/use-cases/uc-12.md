# UC-12 · Un invariant qui protège l’argent ou les données tient sur tous les chemins d’écriture

<RuleMeta />

## Signal

- Un plafond de retrait vérifié par l’endpoint, mais pas par le consumer, le job ou la commande en ligne de commande qui débitent le même wallet.
- Deux use cases qui écrivent le même solde, dont un seul vérifie qu’il reste positif.
- Une écriture qui passe à côté du use case : un script SQL, une migration qui corrige des lignes, une extension de l’ORM (PLC-10, PER-12).

## Pourquoi

Un invariant ne protège rien s’il existe un chemin qui l’ignore. Le solde qui ne doit jamais passer sous zéro y passe par le seul chemin qui ne vérifie pas. Et le prochain point d’entrée oubliera la règle à son tour.

## Exceptions

Aucune.

## Correction

- Lister les chemins qui écrivent la donnée : endpoints, consumers, jobs, commandes en ligne de commande.
- Les faire tous passer par le seul endroit qui vérifie l’invariant. En style tactique, la méthode de l’aggregate qui refuse (AGG-01). En transaction scripts, le script du use case, jamais un adapter (TXS-03).
- Un test viole l’invariant à cet endroit, et vérifie le refus (COV-02).

## Voir aussi

UC-06 pose la même exigence pour l’autorisation. PLC-10 et PER-12 interdisent l’écriture directe en base.
